1. CURRENT ARCHITECTURE

This is a React Native 0.83.1 Android application. App.tsx is the single dashboard screen. Android-specific Kotlin code is under android/app/src/main/java/com/datasentry.

- App.tsx mounts NativeEventEmitter for VpnModule, holds VPN status, alertCount, last-event time, and a feed in React component state.
- MainActivity.kt hosts the React Native component named datasentry.
- MainApplication.kt creates the React host and manually adds datasentryPackage.
- MobileSocNativePackage.kt exposes VpnModule as a legacy React Native module.
- VpnModule.kt checks Android Usage Access, obtains VPN consent using VpnService.prepare, starts/stops VpnPacketCaptureService, and provides playTick.
- VpnPacketCaptureService.kt extends Android VpnService, establishes a restricted TUN configuration, then samples Android traffic statistics on a worker thread.
- EventBridge.kt sends VPN_STATUS and UPLOAD_DETECTED events to React Native on the UI thread, or buffers them in a process-local ConcurrentLinkedQueue.
- The manifest declares INTERNET, FOREGROUND_SERVICE, VIBRATE, PACKAGE_USAGE_STATS, the launcher activity, and the VPN service.
- package.json/package-lock.json define React Native and native UI dependencies. No storage package or navigation library is listed.
- No backend, database, persistent event store, iOS project, or authentication implementation was found.

The long-term product decision is real VPN packet inspection, but the current service is not a packet reader or forwarding VPN. Stage 0 did not change source or begin packet inspection.

2. EXISTING FEATURES IN SOURCE (NOT DEVICE-VERIFIED)

The source contains these user-facing paths:
- Start VPN and Stop VPN buttons.
- Android VPN consent flow through VpnService.prepare and an Activity result listener.
- Usage Access check using AppOpsManager; if missing, VpnModule opens Usage Access settings and rejects the start promise with USAGE_STATS_REQUIRED.

- Stop/revoke code closes the TUN descriptor, interrupts the monitor thread, and emits STOPPED.

These are code paths only. No Android build, device run, permission flow, upload, notification, or regression test was performed in Stage 0, so their successful runtime behavior is not confirmed.

3. GOOGLE PHOTOS MONITORING

No Google Photos-specific implementation exists in the current source:
- No reference to com.google.android.apps.photos or Google Photos was found.
- The monitor is generic by UID. It collects summary buckets, compares UID totals, and resolves a UID to a package name and label through PackageManager.getNameForUid/getApplicationInfo.
- There is no check that the resolved package is Google Photos, and no event is hardcoded to that package.
- If package resolution fails, the service falls back to a package identifier or uid:<number>.
- A per-UID event is selected only when its computed delta reaches 120,000 bytes. If only the device-wide threshold is reached, the event can use another UID or the system UID fallback. That fallback is not reliable evidence that the selected app caused the device-wide traffic.
- The native code reads bucket.txBytes and TrafficStats.getTotalTxBytes. It does not read bucket.rxBytes or TrafficStats receive counters. It therefore observes transmitted bytes only; it does not produce an RX measurement for comparison.
- The data is OS-accounted app/device traffic, not per-photo file size, packet payload, or proof that an upload completed. Event names and UI copy currently overstate the certainty by saying UPLOAD_DETECTED / UPLOAD TRAFFIC DETECTED.
- The current poll interval is 1,500 ms. Each NetworkStatsManager query covers the preceding 15,000 ms, so consecutive intervals overlap. No event ID or duplicate suppression exists; repeated qualifying events are possible.
- Current thresholds are 120,000 bytes per UID and 300,000 bytes device-wide. Severity uses 300,000 and 1,000,000 bytes. The dashboard text instead says >1200B plus frequency in 2 seconds; no such native frequency rule exists.
- NetworkStatsManager calls can fail on missing Usage Access or unavailable data. The service catches SecurityException/other query errors and may continue with missing/partial stats. Delayed or sparse OS stats are not handled as a separately labeled measurement quality state.
- There is no Android NotificationManager/NotificationChannel notification. The current visible notification-like response is a short ToastAndroid message, alongside vibration and sound. The toast does not include app name, package, observed amount, timestamp, or event classification.
- Google Photos behavior and any earlier tested behavior remain unverified. No physical device or adb is available in this workspace.

4. MONITORING AND EVENT FLOW

1. App.tsx calls VpnModule.startVpn.
2. VpnModule requires an Activity, checks Usage Access, then requests Android VPN consent if required.
3. The module starts VpnPacketCaptureService using Context.startService.
4. onStartCommand invokes startCapture. The service emits ACTIVE before establish succeeds.
5. The service configures a TUN address 10.0.0.2/32, MTU 1500, route 10.0.0.0/24, allowBypass, and allows only DataSentry's own package in the VPN. This is intentionally not a global route.
6. The service stores the ParcelFileDescriptor but never reads packets from it. It does not forward traffic.
7. A daemon thread samples TrafficStats total TX and NetworkStatsManager summary TX for Wi-Fi and mobile networks. It skips the DataSentry UID for per-app alerts.
8. On threshold, it emits size, timestamp, severity, UID, optional package/app names, and deviceTotalDeltaBytes.
9. EventBridge emits to the active React Native instance; when unavailable it queues events in memory without a size limit.
10. App.tsx prepends each event to feed, keeps only 60 rows in that component state, increments alertCount, shows generic toast/vibration/tick, and animates the dashboard.
