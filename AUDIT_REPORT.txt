1. EXECUTIVE SUMMARY

DataSentry is a React Native Android dashboard and Kotlin VPN/traffic-statistics simulator. It does not implement packet payload capture. VpnPacketCaptureService establishes a narrowly routed TUN interface but never reads the TUN file descriptor; its events come from Android NetworkStatsManager and TrafficStats byte counters. The dashboard and README call these events packet capture/packet telemetry, which is not supported by the implementation.

The most important confirmed findings are:
- The long-running VpnService is never promoted to a foreground service. Android requires VPN services on supported versions to promote themselves; the current service can be stopped by the OS and has no ongoing notification.
- The app does not read or forward packets. The VPN route covers only 10.0.0.0/24 and only DataSentry is included. Normal internet traffic from other apps is excluded, and ordinary DataSentry internet destinations do not match the TUN route.
- Release builds use the committed default debug keystore and its public default credentials.
- Alerts are derived from moving 15-second operating-system aggregates and global TX counters, not packets. The displayed >1200B / 2-second frequency rule is absent from the native implementation.
- Android 17 is officially released as API 37, but this project compiles and targets API 36. No API 37 or 16 KB page-size result is available; the local environment has no Android SDK/device tooling.
- No tests are present in the working tree; the tracked App.test.tsx is deleted in the pre-existing working tree state.

No user registration, login, backend authentication, API authorization, token/session handling, or credential storage exists in the inspected source. Android VPN consent and Usage Access are operating-system permissions, not user authentication.

3. COMPLETE APPLICATION DATA FLOW

1. App.tsx mounts a NativeEventEmitter for VpnModule and subscribes to UPLOAD_DETECTED and VPN_STATUS. Status defaults to STOPPED; no native status snapshot is requested on mount.
2. On Start VPN, App.tsx calls VpnModule.startVpn(). The module requires a foreground Activity and first checks OPSTR_GET_USAGE_STATS. If denied, it launches Android Usage Access settings and rejects the JavaScript Promise; the user must return and tap Start again.
3. If Usage Access is enabled, VpnService.prepare(activity) is called. Android presents VPN consent if needed. onActivityResult starts the service after approval or rejects after denial. If VPN consent is already present, the service is started directly.
4. VpnPacketCaptureService.onStartCommand calls startCapture(), marks the state active, configures a TUN address 10.0.0.2/32, MTU 1500 and route 10.0.0.0/24, allows bypass, and adds only the DataSentry package to the VPN's allowed-application set. The TUN descriptor is stored but never read or written.
5. A daemon thread polls roughly every 1.5 seconds. It compares TrafficStats.getTotalTxBytes() with the prior sample and queries per-UID NetworkStatsManager summaries for the preceding 15 seconds over Wi-Fi and mobile networks. It emits when a per-UID delta reaches 120,000 bytes or global device TX delta reaches 300,000 bytes. Severity is assigned at 300,000 and 1,000,000 bytes.
6. If a threshold is reached, the native code selects an app UID (or falls back to another UID / system UID), resolves a package name and label where possible, and emits size, timestamp, severity, UID, package, label, and deviceTotalDeltaBytes through EventBridge.
7. EventBridge emits to React Native on the UI thread when the JS runtime is active. Otherwise, it appends events to a process-global unbounded queue. App.tsx normalizes the event, increments the alert count, stores at most 60 feed rows, shows a toast, vibrates, and asks VpnModule to play a tick.
8. Stop VPN sends ACTION_STOP to the service, which closes the PFD, interrupts the polling thread, emits STOPPED, and stops itself. onRevoke also stops the capture state. A network change callback/reconnect loop is not implemented; because the app does not forward packets, this is not a working gateway lifecycle.

PACKAGE_USAGE_STATS is user-granted through Settings, and the code checks AppOps before reading cross-app traffic summaries.

Future authentication recommendation: If DataSentry becomes a multi-user or cloud-synced product, authenticate through a backend. Verify passwords server-side with Argon2id and unique salts; rate-limit login and recovery; add MFA/passkeys according to product risk. Return short-lived, audience-scoped access tokens and rotate opaque refresh tokens with server-side hashes, reuse detection, expiration, and revocation. Enforce authorization/RBAC on every backend resource; never trust roles supplied only by the client. Require HTTPS and normal platform certificate validation. Store only refresh/session material in Android Keystore-backed encrypted storage; never persist a user's password. Logout should revoke the server session and remove local tokens. For a device-only demo with no server data, user accounts add no meaningful authorization boundary and should not be simulated locally.

6. ANDROID 14-16 COMPATIBILITY ASSESSMENT

- API levels: Android 14=34, Android 15=35, Android 16=36. Configured minSdk 24 means installation is intended from API 24 onward.
- VpnService and VpnService.prepare are used with the system consent flow. The manifest includes the required BIND_VPN_SERVICE permission and android.net.VpnService action. The service is exported but protected by the signature-level BIND_VPN_SERVICE gate; it is not an unprotected arbitrary service entry point.
- Android 8/API26 onward requires a VPN service to promote itself to foreground after launch. This code does not call startForeground and does not create an ongoing notification. This is DS-001.
- On API34+ target apps must declare the specific foreground-service type permission when using an FGS. Manifest currently declares specialUse and its subtype property but not FOREGROUND_SERVICE_SPECIAL_USE. A VPN use case may qualify for systemExempted only when the app meets Android's active-VPN eligibility. The appropriate type and permissions need to be selected rather than assuming the current manifest is sufficient.
- POST_NOTIFICATIONS is not present. It is not by itself required to start an FGS, but the app currently has no notification channel or notification at all, so the expected persistent VPN user disclosure is absent.
- PACKAGE_USAGE_STATS is a special system-level Usage Access grant, not an ordinary runtime permission. VpnModule checks AppOps and routes the user to settings. NetworkStatsManager queries other UIDs only with this access. Android calls can throw SecurityException; the service logs and continues with empty/partial results.
- NetworkStatsManager.querySummary exists from API23 and aggregates network use over the requested interval. It may take seconds and is run off the main thread, which is appropriate. Comparing adjacent overlapping 15-second windows is not a packet rate measurement and may repeat/blur events. TrafficStats.getTotalTxBytes is a device-wide TX counter, not per-app attribution.
- ConnectivityManager.TYPE_WIFI and TYPE_MOBILE are used. The code does not use UsageStatsManager. No AppOps query is used to retrieve traffic data except checking the Usage Access mode.
- Android 15 target behavior: edge-to-edge applies because targetSdk is 36. Android 16 target behavior: opt-out is disabled for target 36; gradle.properties edgeToEdgeEnabled=false is not an opt-out. SafeAreaProvider/useSafeAreaInsets are present and add top/bottom padding, but actual cutout/navigation-bar appearance is untested. See DS-010.
- Package visibility: the app resolves labels for other UIDs using PackageManager calls but declares no <queries> or QUERY_ALL_PACKAGES. Android package visibility may prevent some label lookups; fallback to package name or uid exists. This is a low-risk attribution possibility (DS-014), not a claim that the stats API itself is blocked.
- Battery/resource risk: while the loop sleeps for 1.5 seconds, NetworkStatsManager may take several seconds per summary query. There is no battery, CPU, or long-duration profiling. The implementation performs two queries per interval and has no adaptive poll/backoff.
- No deprecated or removed API was found that clearly blocks API34-36. startActivityForResult and ConnectivityManager.TYPE_* are legacy/deprecated paths but remain available. Their effect is not a demonstrated compatibility failure.

7. VPN IMPLEMENTATION FINDINGS

The service configures a TUN interface (10.0.0.2/32, MTU 1500) but only routes 10.0.0.0/24 and includes only DataSentry's package. It intentionally avoids claiming the default route. No packet InputStream/OutputStream loop, parser, payload inspection, proxy, remote VPN gateway, forwarding, NAT, DNS handling, or tunnel socket is implemented. The established PFD is only assigned, closed, and set to null.

Actual telemetry is OS accounting data. The service reads global TX deltas from TrafficStats and per-UID TX summaries from NetworkStatsManager; it does not inspect source/destination addresses, ports, TCP/UDP headers, packet boundaries, TLS/HTTP content, or data payload. Encrypted payload capture is therefore not happening. Calling the feature "packet capture" or "Capturing packets from VPN TUN interface" is misleading. README.md line 43 also says packet sizes are sampled from TUN, which conflicts with the implementation.

The 15-second rolling summary queried each nominal 1.5 seconds is compared to the previous rolling summary. It is not a disjoint interval; repeated bytes can remain in multiple successive snapshots. Global TrafficStats delta may trigger an event for unrelated device traffic and can be attributed to the top observed UID or system fallback. Severity thresholds do not implement the dashboard's stated >1200B and frequency-in-2-seconds rule. These produce uncalibrated usage-spike indicators, not upload detection or packet-size anomalies.

The service does close the PFD during stop/revoke and interrupts the polling thread. It returns START_STICKY, but has no foreground lifetime guarantee, notification, network callback/re-establishment, or persisted state. CPU/battery and attribution accuracy remain unmeasured.

DS-002 | HIGH | P1 | CONFIRMED ISSUE | VPN data plane / feature correctness
Affected: VpnPacketCaptureService.kt:46-76,78-121; App.tsx:184,291; README.md:5,43
Evidence: TUN routes only 10.0.0.0/24, only the app package is allowed, and the established PFD is never read. The monitor instead queries NetworkStatsManager/TrafficStats. README and UI describe packet capture.
Technical explanation: Ordinary internet destinations do not match the configured route, other apps are not included, and no packet-reading/forwarding loop exists. The implementation reports OS-aggregated byte counters, not packet payloads or packet sizes.
Impact: Users can mistake aggregate upload counters for inspected packets or assume other apps are protected/monitored. The simulator does not provide packet-level detection or a full-tunnel privacy/security guarantee.
Recommended correction: Decide whether product scope is OS-level aggregate telemetry or actual VPN inspection. For counter telemetry, rename/status the feature and explain attribution limitations. For packet inspection, design routes, read/parse TUN frames, provide a safe forwarding/gateway model, handle DNS and network changes, and preserve VPN consent/disclosure.
Prerequisites: Product threat model, routing/forwarding architecture, traffic leak policy, battery/resource budget, user disclosure.

DS-004 | MEDIUM | P2 | CONFIRMED ISSUE | Telemetry accuracy / anomaly logic
Affected: VpnPacketCaptureService.kt:86-118,165-184,186-219; App.tsx:224
Evidence: Native code queries a 15,000 ms summary every nominal 1,500 ms, compares adjacent rolling totals, triggers at 120,000 bytes per UID or 300,000 global bytes, and labels severity at 300,000/1,000,000. UI claims >1200B plus frequency in 2 seconds.
Technical explanation: Android querySummary aggregates over its whole requested period. Adjacent 15-second intervals overlap, so activity may remain in multiple successive deltas and trigger repeated/blurred events. TrafficStats is device-wide; if the global threshold fires without a qualifying UID, selection/fallback can attribute a device-level event to an unrelated UID/system. No frequency or packet-size check exists.
Impact: False/repeated/misattributed alerts, severity values disconnected from the UI's stated rule, and no reliable upload/packet detection.
Recommended correction: Define the monitored metric and exact window; use disjoint monotonic samples or a properly designed rolling-window algorithm, separate global from per-app events, make attribution explicit, and show thresholds that match code. If packet-level detection is required, use packet-derived input rather than byte counters.
Prerequisites: Product metric/threshold definition and device calibration across Wi-Fi, cellular, VPN, and idle traffic.

DS-001 | HIGH | P1 | CONFIRMED ISSUE | Android service lifecycle / reliability
Affected: VpnModule.kt:81-102; VpnPacketCaptureService.kt:22-34; AndroidManifest.xml:4-5,30-38
Evidence: VpnModule uses startService. VpnPacketCaptureService never calls startForeground. Manifest declares FOREGROUND_SERVICE and service foregroundServiceType="specialUse" with a subtype, but omits FOREGROUND_SERVICE_SPECIAL_USE. There is no notification channel/notification code.
Technical explanation: A VPN service on Android 8+ must promote itself to foreground after launch to remain alive. A foreground-service declaration alone does not perform that promotion. For Android 14+ the declared type also requires its type-specific permission when promoted.
Impact: The OS can stop the long-running VPN after its temporary start allowance; status/monitoring can stop while UI indicates active. A future promotion using the current specialUse declaration can fail permission checks.
Recommended correction: Establish a user-visible ongoing VPN notification and promote the service promptly; select the valid VPN FGS type and matching permission for each supported platform, handle notification denial appropriately, and keep stop/revoke/process restart state synchronized.
Prerequisites: FGS type eligibility decision, notification channel/text, API 26-37 lifecycle tests, Play Console declaration if applicable.

DS-006 | MEDIUM | P2 | CONFIRMED ISSUE | Native event lifecycle / memory
Affected: EventBridge.kt:13-55; VpnPacketCaptureService.kt:105-118
Evidence: pendingEvents is a ConcurrentLinkedQueue with no bound, expiry, persistence limit, or backpressure. emit adds when there is no active React instance; flushPending runs only after a React context is set.
Technical explanation: A continuing service can queue events while the React instance is absent/inactive. Repeated events are retained for the process lifetime until a later context drains them; stale alert rows are replayed.
Impact: Memory growth under repeated qualifying traffic and stale/duplicated alerts after reload. OOM is a plausible but workload-dependent consequence.
Recommended correction: Bound/coalesce the queue, drop expired telemetry, retain only current VPN state separately, and avoid queuing events that are no longer actionable. Expose delivery/drop counts for diagnostics.
Prerequisites: Event delivery semantics and lifecycle tests with JS reload, backgrounding, and process recreation.

DS-007 | MEDIUM | P2 | POTENTIAL ISSUE | VPN startup/error state
Affected: VpnPacketCaptureService.kt:41-75
Evidence: ACTIVE is emitted at line 44 before Builder.establish() at line 68. The establish call is not in a catch/finally block; only addAllowedApplication failure and a null descriptor are handled.

Recommended correction: Emit ACTIVE only after establishment and foreground promotion succeed; catch startup exceptions, close partially acquired resources, report a typed failure, and always reconcile service/JS state.
Prerequisites: Typed native error contract and lifecycle tests for denied consent, revoke, duplicate start, and establish failure.

Architecture assessment:

12. RECOMMENDED AUTHENTICATION ARCHITECTURE

There is no current authentication system to secure. If account-based sync or remote policy management is introduced, use a backend as the authority. Perform Argon2id password verification on the server with unique salts and rate limits; never store passwords on the device. Issue short-lived access tokens and rotating revocable refresh sessions. Enforce authorization on every API request, including roles and tenant boundaries. Require HTTPS and platform certificate validation. Store refresh/session tokens using Android Keystore-backed encryption, clear them on logout, and revoke sessions server-side. Add login/recovery protections and optional MFA/passkeys based on the threat model. Keep local-only VPN consent and Usage Access separate from account authentication.

15. FINAL ASSESSMENT

The repository is a small Android-only React Native demo with a useful UI/native event bridge, but the implementation does not capture packet payloads. It samples operating-system TX counters, and its VPN interface is narrowly routed and unread. The UI/README overstate what the native code measures. The long-running VPN service lacks foreground promotion, release artifacts use the default debug signing identity, and detector windows/threshold descriptions are inconsistent. No authentication/backend exists, and Android OS permission grants are not user accounts.

Android 14-16 have a confirmed VPN service lifecycle defect and unverified edge-to-edge/native alignment behavior. Android 17 API 37 is publicly released, but this project only compiles and targets API 36 and was not tested on any Android device in this audit environment. Do not claim API 37 or 16 KB compatibility until a real build and test matrix passes. No code was modified. AUDIT_REPORT.txt is the sole audit artifact.
